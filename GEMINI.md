# 🛡️ Cube Siege — Agent & Engineer Guide

Правила разработки Cube Siege для Gemini / Antigravity и инженеров. Настройка среды и команды: [docs/AGENT_SETUP.md](docs/AGENT_SETUP.md).

Для Codex этот контракт дополняется [AGENTS.md](AGENTS.md): там описаны привязка чата и подтверждение завершения review run.

## Таймауты и ожидание

Перед потенциально долгой командой или ожиданием MCP прочитай [docs/OPERATION_TIMEOUTS.md](docs/OPERATION_TIMEOUTS.md). Задавай общий deadline и условие завершения; сервисы без естественного конца запускай в управляемом фоне, проверяй готовность за ограниченное время и не жди их выхода. Таймаут не является PASS.

## MCP: ментор и изображения

В Antigravity настроен `chatgpt-project-bridge`. Перед первым обращением прочитай [docs/MCP_BRIDGE.md](docs/MCP_BRIDGE.md) и проверь `bridge_status`. Используй реальные имена инструментов из текущей сессии; наличие записи в конфиге ещё не подтверждает подключение браузера.

- **`ask_mentor`**: обращайся после двух безуспешных попыток устранить одну причину ошибки; перед изменением контракта между системами, если после чтения кода/тестов остаётся техническая неопределённость; для разбора сложного замечания reviewer, которое не удаётся подтвердить локально. Передавай конкретный вопрос, ограничения, факты, уже проверенные гипотезы и нужные фрагменты кода/изображения. Простые правки и вопросы, решаемые поиском по проекту, выполняй самостоятельно.
- **`generate_image`**: используй для необходимых по задаче растровых концептов, референсов, текстур, иллюстраций и правок изображений. Укажи назначение, стиль, ракурс, фон/прозрачность и неизменяемые признаки. SVG, геометрию, сцены и проверочные скриншоты создавай соответствующими инструментами проекта. Сгенерированный концепт не доказывает работу игры и не становится утверждённым дизайном автоматически.
- В рамках утверждённой задачи эти обращения выполняй самостоятельно, без согласования каждого запроса. Ментор консультирует, но не принимает решения за Game Designer, не расширяет scope и не заменяет тестирование или независимое PR review.
- Оба инструмента возвращают задание: сохрани `id` и исходный `request_key`, затем вызывай `get_job(job_id=id, wait_seconds=25)` до конечного статуса. Не создавай дубликаты при ожидании или потере ответа. При `blocked`, `failed`, `uncertain` действуй по руководству и продолжай независимую работу.
- После `complete` прочитай ответ/открой полученные изображения, проверь результат по задаче и сохрани происхождение используемых файлов. Не заявляй успешную консультацию или генерацию только по факту отправки запроса.

## 1. Роли и полномочия

* **Пользователь**:
  * **Game Designer** и **Product Owner**.
  * Единственный источник окончательных решений о геймплее, правилах, балансе и скоупе.
* **Gemini (Агент)**:
  * **Software Engineer** и технический исполнитель.
  * Архитектор исключительно в пределах уже утверждённого игрового дизайна.

### Что Gemini МОЖЕТ решать самостоятельно
* Внутренняя архитектура и структура классов.
* Разделение ответственности (SOLID, Single Responsibility).
* Алгоритмы, структуры данных и интерфейсы.
* Написание модульных, интеграционных и дымовых тестов.
* Оптимизации, не меняющие игровой процесс.
* Внутренняя организация и форматирование кода.

### Что Gemini НЕ МОЖЕТ придумывать самостоятельно
* Новые игровые механики и правила классов.
* Баланс: числа урона, здоровья, скорости, радиусы, кулдауны, длительности.
* Экономику, цены построек, формулы дропа и прогрессию.
* Поведение, которого нет в задании, GitHub Issue или каноническом GDD.

> [!IMPORTANT]
> Если для реализации требуется недостающее геймдизайнерское решение:
> **НЕ УГАДЫВАТЬ.** Явно пометить задачу как `DESIGN DECISION REQUIRED`, описать технические альтернативы и реализовать только независимые части.

> [!IMPORTANT]
> После явной команды пользователя «приступай / реализуй / исправь», а также при автоматическом запуске из PR review loop, **не создавать `implementation_plan.md`, не просить проверить план и не ждать дополнительного подтверждения**. Выполнить внутреннее планирование и сразу перейти к коду и тестам. Исключение — только реальный `DESIGN DECISION REQUIRED`; независимые части задачи всё равно выполнить.
> Существующие незакоммиченные изменения вне скоупа текущей задачи принадлежат пользователю: не откатывать, не добавлять в индекс, не коммитить и не изменять их.
> В автоматическом PR review-loop режиме не публиковать собственные reviews и статусные комментарии в GitHub. Единственное исключение — визуальные вложения по [docs/PR_VISUAL_MEDIA.md](docs/PR_VISUAL_MEDIA.md). Результат сообщать в текущем чате. Для Antigravity push commit является сигналом завершения; Codex обязан также подтвердить run через `complete_run.py --run-id` по [AGENTS.md](AGENTS.md). Самостоятельно не merge PR.

## 2. Иерархия источников истины

### Что игра ДОЛЖНА делать (Спецификация)
1. Последнее прямое указание пользователя.
2. Контракт задачи: GitHub Issue (с учётом последних комментариев и правок).
3. `docs/GDD.md` (Канонический дизайн-документ).
4. Утверждённые технические документы (`docs/ARCHITECTURE.md`, `docs/BACKLOG.md`).

### Что игра ДЕЛАЕТ сейчас (Фактическая реализация)
1. Фактически выполненные проверки и наблюдаемое поведение с указанием версии кода и условий запуска.
2. Текущий исполняемый код (`scripts/`, `src/`) и тесты (`tests/`); наличие теста без запуска не доказывает PASS.
3. Сцены и ресурсы Godot (`scenes/`, `assets/`).
4. `docs/STATUS.md` (Сводка статуса; проверять по коду и результатам запуска).
5. `docs/ARCHITECTURE.md`.
6. `README.md` (*README никогда не является доказательством существующей реализации*).

Противоречие требований разрешай по иерархии спецификации; запрашивай только недостающее дизайнерское решение. Расхождение требований и реализации фиксируй как дефект/ограничение: существующий код или тест не отменяет утверждённое поведение. Совет ментора — проверяемая гипотеза, а не новый источник требований.

## 3. Issue-Driven Development

Основной рабочий процесс разработки строится через GitHub Issues. Явный запрос пользователя без Issue также является контрактом задачи: не выдумывай номер Issue и не блокируй исполнение ради его создания.

* **GitHub Issue — авторитетный контракт реализации**. Агент обязан прочитать Issue полностью, включая комментарии и последние утверждённые design revisions.
* **Приоритет ревизий**: Последнее явно утверждённое изменение требований в Issue имеет приоритет над более старой формулировкой.
* **Неизменность контракта**: Gameplay specification, Rules, Out of Scope, Design Constraints и Acceptance Criteria запрещено самостоятельно менять или переосмысливать.
* **Scope discipline**: Не чинить попутный технический долг, не добавлять "улучшений" вне скоупа Issue.
* **Ветки и PR**:
  * Каждая задача реализуется в отдельной ветке: `feat/N-description`, `fix/N-description`, `refactor/N-description`.
  * Создавать PR только через `python tools/review_loop/create_pr.py -- <аргументы gh pr create>`; прямой `gh pr create` не сохраняет гарантированную привязку к GUI-чату.
  * Pull Request обязан содержать чек-лист критериев приёмки; `Closes #N` (или `Fixes #N`) добавляй только для существующей Issue, которую PR действительно закрывает.
  * Issue не закрывается вручную — закрытие происходит автоматически при merge PR.

## 4. Технологическая политика

* **Основной gameplay-слой — GDScript**. UI, стейт-машины, композиция сцен, высокоуровневая оркестрация и логика способностей реализуются на GDScript.
* **C++ GDExtension используется исключительно для**:
  * Подтверждённых профилированием горячих участков (hot paths).
  * Векторного поля маршрутизации (2D Flowfield Pathfinding).
  * Массовой симуляции толпы (500+ юнитов, MultiMesh).
  * Крупных пулов снарядов (Bullet hell / Projectiles).
* Запрещено переносить код в C++ «ради использования C++». Публичная граница C++ ↔ Godot должна быть минимальной, строго типизированной и документированной.

## 5. Правило минимального изменения

* Сначала исследовать существующий код и связи сцен.
* Изменять строго минимально необходимую область файлов.
* Никакого попутного рефакторинга соседних файлов.
* Не менять формат сохранений (`SaveManager`) без версионирования и миграций.
* Не модифицировать submodule `godot-cpp`.
* Не редактировать кэши (`.godot/`, `.sconsign.dblite`) и временные файлы.
* Не обновлять версии зависимостей без явного требования.

## 6. Definition of Done (Критерии готовности задачи)

Для создания/полировки gameplay VFX начни с [docs/vfx/START_HERE.md](docs/vfx/START_HERE.md):
там готовые production образцы, ограниченные capture-команды, rig inspection и
передача source assets из `game_assets`. Технический gate не выдаёт художественный approval.

Задача **НЕ** считается выполненной только потому, что код написан.

Для PR с визуальными изменениями после создания и после push исправлений обязательно публикуй актуальные медиа (PNG и, для анимаций/VFX, доступные видео) как GitHub-вложения в отдельном комментарии через `gh pr comment --attach`. Прочитай и выполни [docs/PR_VISUAL_MEDIA.md](docs/PR_VISUAL_MEDIA.md): SHA коммита, исходные references, рендеры, проверка загрузки и маркер автоматического комментария обязательны. Одних файлов в репозитории или ссылок в описании PR недостаточно. Для изменений только документации без визуального результата медиа не требуются.

Перед объявлением задачи завершённой обязательно:
1. `git diff` — проверить отсутствие лишних правок, отладочных принтов и мусора.
2. Если затронуты скрипты, сцены, ресурсы или конфигурация игры — проверить headless-импорт Godot (отсутствие битых ресурсов и скриптов).
3. Если затронут C++ — собрать GDExtension (`scons custom_api_file=extension_api.json ...`).
4. Запустить проверки затронутой области. Для комплексных изменений игры — `python tools/verify.py` (сборка, импорт, GUT, Python и smoke-проверки); отдельный запуск GUT не равнозначен полному аудиту. Для изменений только документации — проверить ссылки, команды и непротиворечивость правил; сборка игры не требуется.
5. Если затронуто runtime-поведение — запустить игру и убедиться в отсутствии runtime errors.
6. Проверить каждый пункт **Acceptance Criteria**.
7. При визуальных изменениях — зафиксировать скриншот.
8. Предоставить прозрачный отчёт:
   * Что изменено.
   * Как проверено.
   * Какие тесты пройдены.
   * Что не удалось проверить и какие риски остались.
