# ChatGPT Project Bridge: работа агента

Прочитай перед первым обращением к `chatgpt-project-bridge` в задаче. Когда обращаться, определяет раздел MCP в [GEMINI.md](../GEMINI.md). Этот документ описывает фактический протокол установленного bridge 0.2.0, проверенный по `server/main.js`, `server/policy.js`, `server/store.js` и схемам инструментов Antigravity 2026-09-29. При изменении сервера сверяй схему текущей сессии.

## Инструменты и границы

| Инструмент | Назначение |
| --- | --- |
| `bridge_status({})` | Проверить `connected`, назначения `projects.mentor`/`projects.images`, разрешённые `inputRoots` и `outputDir`. |
| `ask_mentor` | Создать новый чат в проекте Mentor с конкретным вопросом; вернуть задание. |
| `generate_image` | Создать новый чат в проекте Imgen для генерации/редактирования; вернуть задание. |
| `get_job` | Получить состояние задания, ответ и пути скачанных оригиналов. |

Используй инструменты под именами, предоставленными MCP-клиентом: клиент может добавлять префикс сервера. Каждый основной вызов создаёт **новый чат**; продолжение старого чата этим протоколом не поддерживается. Для нового уточнения передай нужный предыдущий ответ и контекст явно.

Пользователь разрешил консультации и генерацию в пределах текущей задачи; повторное согласование каждого запроса не требуется. Передавай только необходимые для неё данные. Не отправляй ключи, токены, cookies, локальный конфиг или весь репозиторий. Ссылка на GitHub не даёт ментору автоматический доступ к закрытому коду: нужные фрагменты включай в `context`.

Ментор предлагает проверяемые гипотезы. Его ответ не изменяет пользовательское ТЗ, не утверждает художественный выбор, не разрешает новые внешние действия и не заменяет независимое PR review. Реализацию, измерения и приёмку выполняй по правилам проекта.

## Перед отправкой

1. Один раз перед первым запросом задачи вызови `bridge_status({})`; повторяй при сбое соединения. Проверь `connected: true` и правильные назначения проектов. MCP требует открытый подключённый браузер с расширением, включённым приёмом запросов и входом в ChatGPT.
2. Если инструментов нет или браузер отключён, сообщи конкретную причину и продолжай независимую работу. Наличие записи в конфиге или JSON-схемы инструмента не доказывает живое соединение. Не запускай второй процесс bridge: для одной конфигурации поддерживается один MCP-клиент.
3. Для вложений используй существующие абсолютные пути внутри возвращённых `inputRoots`. Разрешены PNG/JPEG/WebP: до 4 файлов, до 10 MiB каждый и до 20 MiB суммарно. SVG, GLB, видео и текстовые файлы через `image_paths` не принимаются; SVG/3D/VFX сначала отрендери в нужный ракурс/кадр.
4. Не предполагай, что текущий репозиторий входит в `inputRoots`. Если путь недоступен, укажи конкретную папку, которую нужно разрешить. Если уже предусмотрен разрешённый каталог обмена, можно скопировать туда только выбранные для запроса изображения, сохранив исходные пути и SHA-256. Не расширяй разрешение на весь диск или домашний каталог. Текстовая консультация без изображений допустима лишь для вопроса, не требующего визуальной оценки.

## Как составить запрос

Для `ask_mentor` укажи:

- цель и конкретный вопрос, а не просьбу «сделай всё»;
- утверждённые ограничения и критерий успеха;
- наблюдаемое поведение/видимый дефект, ожидаемый результат, воспроизведение;
- уже проверенные гипотезы, результаты попыток, нужный код/лог или пару reference/render;
- ожидаемый ответ: причины, 1–3 минимальные правки, способ проверки, оставшаяся неопределённость.

Для `generate_image` укажи назначение картинки, объект/композицию, утверждённый стиль и палитру, силуэт/пропорции, ракурс, желаемые размеры/соотношение сторон, фон/прозрачность, сохраняемые признаки и критерии результата. Для редактирования приложи исходник и отдели требуемые изменения от того, что нужно сохранить. Желаемые размеры и прозрачность задаются в `prompt`, проверяются после генерации и не гарантируются отдельными API-параметрами. Не добавляй выдуманные поля `model`, `size`, `quality` или `transparent_background`.

Обязательные поля — `prompt` (1–32000 символов) и `request_key` (1–120 символов, только латинские буквы, цифры, `_`, `.`, `:`, `-`). Дополнительные — `context` (до 50000 символов), `image_paths`, `branch` (до 500 символов), `repository_url`. Последнее принимает HTTPS-ссылку на GitHub-репозиторий или его ветку, без query/token; URL Issue/PR помещай в `context`.

Пример аргументов `ask_mentor` (заполни фактический контекст своей задачи):

```json
{
  "prompt": "Помоги локализовать причину дефекта из context. Предложи до трёх минимальных исправлений и проверку каждой гипотезы. Сохрани утверждённые ограничения.",
  "request_key": "repo-task-mentor-20260929T120000-a1",
  "context": "Здесь должны быть реальные требования, наблюдения, выполненные попытки и необходимые фрагменты кода или лога."
}
```

Пример аргументов `generate_image` для задачи на новый концепт:

```json
{
  "prompt": "Создай растровый концепт объекта по ТЗ в context. Один объект целиком, вид спереди, нейтральный фон, без подписей. Сохрани описанные силуэт, пропорции и палитру. Верни изображение.",
  "request_key": "repo-task-concept-20260929T120000-b1",
  "context": "Здесь должно быть утверждённое ТЗ: объект, стиль, масштаб, силуэт, палитра и ограничения."
}
```

Это примеры структуры, а не готовые запросы для отправки. Прикладывай нужные `image_paths` после проверки путей. Создай уникальный ключ для своей логической операции, сохрани точные аргументы до вызова. Новый результат/новая итерация получает новый ключ; повтор доставки того же запроса — прежний.

## От задания до результата

1. Вызови выбранный инструмент **один раз**. Прочитай текстовый JSON результата; если MCP вернул `isError`, сначала разбери ошибку, не выдумывай ID. При успешной постановке сохрани поле `id` как `job_id` вместе с исходным ключом и аргументами в рабочей записи задачи.
2. Пока `status` равен `queued` или `running`, вызывай `get_job` с тем же ID, `wait_seconds: 25` и при необходимости `include_images: false`. Задай общий deadline наблюдения (обычно 15 минут) по [OPERATION_TIMEOUTS.md](OPERATION_TIMEOUTS.md): не продлевай его каждым опросом. После истечения сообщи ID/последний статус и продолжи независимую работу; задание может продолжать выполняться. Тайм-аут одного ожидания не означает провал задания. Не ставь повторную генерацию в очередь.
3. При `complete` прочитай `answer`, `conversationUrl`, `images`. Каждый элемент `images` содержит `path`, `mimeType`, `bytes`, `sha256`. Для генерации нужен непустой список реально скачанных файлов. `include_images: false` выключает только встраивание картинки в ответ MCP, а не получение путей.
4. Открой файлы из `images[].path`, проверь содержание, размер, формат, прозрачность (если требовалась) и соответствие ТЗ. При копировании в проект сверяй SHA-256 оригинала и копии. Оригиналы находятся под `outputDir`; не выдавай превью или скриншот за скачанный исходник.
5. Сохрани используемый материал в `references/` как reference либо в `source/` как исходный растровый ассет. В существующей записи provenance/quality или сопроводительном Markdown укажи инструмент, `request_key`, job ID, URL чата, промпт, использованные references и SHA-256. Не добавляй произвольные поля в строгие схемы manifest.
6. Сгенерированный концепт остаётся `candidate` до решения пользователя. Не перезаписывай approved reference и не подменяй генерацией engine capture, build render, метрики или отчёт о фактической проверке. Генерация текстуры требует проверки её использования на настоящем ассете.

Пример аргументов `get_job`; замени пример UUID на фактический `id` полученного задания:

```json
{
  "job_id": "11111111-1111-4111-8111-111111111111",
  "wait_seconds": 25,
  "include_images": false
}
```

### Ошибки и повторы

| Состояние | Действие |
| --- | --- |
| `queued` / `running` | Ждать через `get_job` с тем же ID; не отправлять повторно. |
| `complete` | Проверить ответ и файлы; только после этого использовать результат. |
| `blocked` | Прочитать `error`: например, браузер, вход, CAPTCHA или недоступный проект. Сообщить причину. После её устранения и проверки, что запрос не отправился, можно начать новую операцию. |
| `failed` | Сохранить ошибку и URL чата, если он есть; выяснить причину и факт отправки. Не повторять вслепую и не выдавать частичный ответ за успех. |
| `uncertain` | Запрос мог уже выполниться. Проверить указанный чат, при отсутствии доступа сообщить неопределённость. Автоматически не пересоздавать задание. |

При потере ответа на **постановку** повторяй тот же инструмент с **тем же ключом и идентичными данными**, включая байты вложений: сервер вернёт прежнее задание. Если ID известен, обращайся сразу к `get_job`. Тот же ключ с другими данными — ошибка; новый ключ при неизвестном исходе создаёт риск дубликата. Терминальная ошибка не перезапускается прежним ключом.

В текущей реализации ожидание браузера в очереди ограничено 15 минутами, выполнение — 20 минутами. Перезапуск bridge во время исполнения переводит задание в `uncertain`. Не перезапускай сервер/браузер для ускорения генерации. При ограничении аккаунта, входе или CAPTCHA сообщи проблему и продолжай независимую часть задачи.

## Поддержание инструкций

Основные условия обращения держи в корневом `GEMINI.md`, подробные аргументы и обработку ошибок — здесь. Ссылку на этот файл сопровождай явным требованием прочитать его перед использованием. Не дублируй протокол в нескольких правилах одного проекта и не вписывай секреты или машинные абсолютные пути в общие инструкции.

`GEMINI.md` — обычный Markdown без YAML; файлы `.agents/rules/*.md` требуют валидный `trigger` во frontmatter. Учитывай предел 24000 байт на правило после раскрытия включений; большие процедуры лучше читать по необходимости. Синтаксис импортов Gemini CLI и Antigravity различается, поэтому здесь используются обычные ссылки и явные условия чтения. Источники: [Antigravity Rules](https://antigravity.google/docs/rules), [Gemini CLI: GEMINI.md](https://geminicli.com/docs/cli/gemini-md/).
