# Таймауты и завершение операций

Эти правила обязательны для Gemini / Antigravity и Codex.

- До запуска потенциально долгой операции задай **условие успеха, общий срок ожидания и способ остановки**. Наличие вывода в консоли само по себе не отменяет общий срок.
- Для конечных команд используй настоящий timeout процесса или API. `yield_time_ms`, возврат session ID и timeout одного опроса ограничивают только ожидание ответа инструмента — они не завершают работающий процесс.
- Ориентиры, если у проекта/инструмента нет более точных лимитов: Git/CLI/сетевой запрос — 30–60 секунд; запуск сервера и readiness — 30 секунд; тесты/импорт — 5 минут; сборка — 10 минут; генерация изображения — до 15 минут. Выбирай разумный лимит по объёму работы, а не механически один для всего.
- У цепочки запросов, polling и retry должен быть **единый deadline**: не начинай отсчёт заново при каждом `running` или повторе. Ограничивай число повторов; не запускай бесконечные `while true` в ожидании успеха.
- Для асинхронного MCP сохраняй job ID и request key. У bridge один `get_job` может ждать до 25 секунд; также нужен общий лимит наблюдения (обычно 15 минут). По его истечении сообщи ID и последний статус, продолжи независимую работу. Это **не отменяет удалённое задание**: позднее проверяй тот же ID, не создавай дубликат. Не повторяй отправку с неопределённым результатом.
- Watcher, dev-server, editor и игра в обычном режиме не обязаны завершаться. Запускай нужный сервис в управляемом фоне, сохрани PID/службу и лог, проверь readiness за ограниченное время и продолжай задачу. Не жди выхода бесконечного сервера. Для smoke-проверки используй конечный режим, число кадров/итераций или отдельный таймаут.
- Долгоживущий сервис может работать без общего срока жизни **только когда это цель его запуска** (например, постоянный watcher пользователя). Его HTTP/CLI-вызовы, readiness и отдельные задания всё равно ограничены по времени; нужны контролируемая остановка и восстановление после сбоя.
- Для foreground-процессов на Python используй `subprocess.run(..., timeout=seconds)`. Для `Popen` — `wait(timeout=seconds)`/deadline и контролируемую остановку собственного процесса и его дочерних процессов. На Windows запускай фоновые помощники скрыто.
- При таймауте сначала сохрани доступную диагностику; останови только запущенный этой задачей временный процесс. Не завершай чужие процессы по общему имени вроде `python` или `godot`. Для удалённого сервиса используй отмену только если она поддерживается и не затрагивает чужую работу.
- Различай `TIMEOUT`, `FAIL` и `PASS`. Таймаут не доказывает ни успех, ни логическую ошибку результата. Не ставь completion marker и не объявляй проверку пройденной. Укажи команду/операцию, лимит, статус и место лога.
- Не увеличивай лимит и не повторяй зависший шаг бесконечно. Сначала прочитай лог и проверь прогресс; допускается обоснованный конечный повтор с новым общим сроком. Для неопределённой доставки сначала проверь существующий запрос/чат.

Во время долгой работы сообщай о существенном прогрессе или проблеме примерно раз в минуту; отдельные блокирующие ожидания делай короткими, чтобы оставаться доступным пользователю.
