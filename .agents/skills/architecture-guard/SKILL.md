# Architecture Guard Skill

Инженерный фильтр архитектурной чистоты и предотвращения деградации кодовой базы.

## Фундаментальный принцип
**Архитектура должна обслуживать Issue, но Issue не является лицензией на слом архитектурных инвариантов.**

Если буквальная реализация задачи из Issue подталкивает к:
- Созданию нового God Object;
- Второму владельцу существующего состояния;
- Циклической зависимости между модулями;
- Прямому связыванию геймплея с UI-нодами (`Label`, `Control`);
- Нарушению границы GDScript ↔ C++;
- Дублированию схемы сохранений без миграции;

Инженер **обязан** выбрать другое техническое решение, полностью сохраняющее утверждённый геймплейный контракт. Если конфликт неразрешим без изменения геймдизайна — не менять правила самостоятельно, а явно запросить решение у геймдизайнера (`DESIGN DECISION REQUIRED`).

## Чек-лист проверки перед изменениями

1. **Владение состоянием (State Ownership)**:
   - Кто владеет этими данными? Существует ли единственный источник истины?
   - Не создаём ли мы параллельный кэш, который может рассинхронизироваться?
2. **Направление зависимостей (Dependency Direction)**:
   - Разделены ли уровни:
     - **Domain**: правила боя, характеристики персонажей, расчет урона.
     - **Presentation**: спрайты, меши, звуки, UI, анимации.
     - **Infrastructure**: ввод, файлы сохранений, сетевые запросы.
   - Зависимости должны идти внутрь: представление знает о домене, но домен **не знает** о представлении.
3. **Слабая связанность (Decoupling)**:
   - События между несвязанными системами передаются через `EventBus` (`EventBus.player_health_changed.emit(...)`).
   - Использовать сигналы вместо прямого вызова методов вверх по дереву сцен.
4. **Контроль размера классов (Anti-God Object)**:
   - Если класс превышает 400–500 строк или выполняет разнородные задачи (например, перемещение + драфт карт + строительство) — новую логику выносить в специализированные компоненты или ресурсы.
