# Workflow: /implement-feature

Полный цикл безопасной реализации новой игровой механики на основе контракта GitHub Issue.

## Пошаговый сценарий

### Шаг 1: Получение и чтение Issue
1. Получить текст Issue по номеру (например, через `gh issue view <number>`).
2. Прочитать полное описание, последние комментарии пользователя и актуальные ревизии требований.
3. Извлечь неизменяемый контракт:
   - Цель (Goal);
   - Игровое поведение (Player-facing behavior);
   - Правила и формулы (Gameplay rules);
   - Ввод (Inputs);
   - Состояния (States);
   - Краевые случаи (Edge cases);
   - Ограничения дизайна (Design constraints);
   - Вне рамок задачи (Out of scope);
   - Критерии приёмки (Acceptance criteria).

### Шаг 2: Анализ существующего кода и выявление белых пятен
1. Изучить связанные скрипты в `scripts/`, сцены в `scenes/` или нативный код в `src/`.
2. Проверить контракт на противоречия.
3. Если для реализации не хватает геймдизайнерского решения — **не додумывать**.
   - Объявить `DESIGN DECISION REQUIRED`;
   - Описать технические варианты;
   - Заниматься только независимой частью.

### Шаг 3: Технический план и подготовка ветки
1. Составить технический план реализации (без пересмотра утверждённого геймдизайна).
2. Создать ветку задачи от `main`:
   ```bash
   git checkout -b feat/<issue-number>-<short-description>
   ```

### Шаг 4: Тесты и пошаговая реализация
1. Написать юнит/смоук-тесты в `tests/`, фиксирующие ожидаемое поведение.
2. Внести минимальные изменения в кодовую базу.
3. Соблюдать правила `gdscript.md` и `cpp-gdextension.md`.

### Шаг 5: Валидация в движке и плейтест
1. Проверить импорт и синтаксис в Godot:
   ```bash
   godot --headless --editor --quit
   ```
2. Если затронут C++ — собрать GDExtension (`scons custom_api_file=extension_api.json ...`).
3. Запустить проект и протестировать поведение:
   ```bash
   godot --headless --path . --quit-after 100
   ```
4. Проверить логи консоли на отсутствие ошибок и предупреждений.

### Шаг 6: Проверка Acceptance Criteria и подготовка PR
1. Проверить каждый критерий приёмки из Issue вручную и тестами.
2. Просмотреть полный `git diff`.
3. Создать Pull Request с привязкой `Closes #N` и чек-листом Acceptance Criteria.
