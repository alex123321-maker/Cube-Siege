# Issue-Driven Development Rule

Правила работы с задачами через GitHub Issues и Pull Requests:

## 1. Авторитетный жизненный цикл задачи
Каждая инженерная задача запускается от утверждённого GitHub Issue:
```text
Issue #N
  ↓ Чтение Issue, контекста и утверждённых комментариев
  ↓ Анализ существующей кодовой базы и сцен
  ↓ Проверка неоднозначностей и Design Decisions
  ↓ Составление технического плана реализации
  ↓ Создание ветки задачи (feat/N-..., fix/N-...)
  ↓ Написание/актуализация тестов
  ↓ Минимальная реализация
  ↓ Валидация в Godot (импорт + запуск)
  ↓ Проверка каждого пункта Acceptance Criteria
  ↓ Ревью git diff
  ↓ Создание Pull Request (Closes #N)
  ↓ Ревью пользователем → Merge → Автоматическое закрытие Issue
```

## 2. Дисциплина границ задачи (Scope Discipline)
- **Одна Issue = строгие границы (Scope)**.
- Запрещено добавлять в рамках Issue:
  - Новые механики или альтернативные варианты способностей;
  - Самовольные балансные правки (скорость, здоровье, кулдауны);
  - Посторонний рефакторинг соседних систем;
  - Дополнительные «улучшения» и фичи, которых нет в тексте задачи.
- Если в ходе работы замечен технический долг или баг вне скоупа:
  - **НЕ чинить его в текущей ветке**;
  - Зафиксировать как потенциальный follow-up или предложить создание отдельной технической задачи.

## 3. Политика именования веток
- Для Issue #N ветка создаётся от актуального `main`:
  - Новая механика: `feat/N-short-slug`
  - Багфикс: `fix/N-short-slug`
  - Технический рефакторинг: `refactor/N-short-slug`
  - Инфраструктура: `chore/N-short-slug`
- Прямая работа в `main` запрещена.

## 4. Требования к Pull Request
- Каждый PR должен быть привязан к одной Issue и содержать в описании:
  1. Ссылку на задачу и ключевое слово закрытия: `Closes #N` или `Fixes #N`.
  2. Краткое резюме инженерных изменений.
  3. Чек-лист **всех** Acceptance Criteria задачи:
     - `[x] Критерий 1 — проверен (тест test_foo.gd)`
     - `[x] Критерий 2 — проверен (визуально в игре)`
     - `[ ] Критерий 3 — НЕ проверен (причина: ...)`
     *Категорически запрещено отмечать критерий проверенным, если проверка не выполнялась.*
  4. Список пройденных тестов и результаты запуска игры.
  5. Скриншоты для любых визуальных изменений интерфейса или сцен.
  6. Оставшиеся риски или известные ограничения.
- Issue не закрывается вручную — она должна закрываться автоматически GitHub при мерже PR.

## 5. Обработка изменений дизайна в процессе (Design Revisions)
- Если во время работы над Issue требования были дополнены пользователем в комментариях:
  1. Перечитать обновлённый текст задачи и авторские комментарии пользователя.
  2. Определить, какие части уже написанного кода или тестов устарели.
  3. Скорректировать план реализации и тесты.
  4. Продолжить работу по актуальной версии контракта.
- Принимать в качестве ревизий дизайна только явные указания пользователя (Game Designer / Product Owner), а не случайные догадки.
