# Project Contract Rule

Всегда применяемые правила для разработки проекта Cube Siege:

## 1. Роли
- **Пользователь**: Game Designer & Product Owner. Утверждает геймплей, баланс, правила и скоуп.
- **Gemini**: Software Engineer & Technical Implementer. Принимает технические решения (структура классов, интерфейсы, тесты, алгоритмы), но строго следует утверждённому дизайну.

## 2. Запрет на самовольное изменение геймдизайна
- Запрещено менять кулдауны, значения урона, здоровье, радиусы, правила классов, длительности и экономику, если это прямо не указано в задаче или Issue.
- При отсутствии геймдизайнерского решения объявлять `DESIGN DECISION REQUIRED`, предлагать технические опции и реализовывать только независимые части.

## 3. Иерархия источников истины
- Спецификация: Прямое указание пользователя > Контракт Issue > `docs/GDD.md` > `docs/ARCHITECTURE.md`.
- Реализацию подтверждают фактические запуски/измерения и актуальные код, тесты, сцены/ресурсы. Наличие теста без запуска не доказывает PASS; `docs/STATUS.md` и README требуют сверки. Код и тесты не отменяют требования пользователя.
- Ментор через `chatgpt-project-bridge` даёт проверяемые рекомендации, а не дизайн-решения или PR approval. Условия обращения — в [GEMINI.md](../../GEMINI.md), протокол — в [docs/MCP_BRIDGE.md](../../docs/MCP_BRIDGE.md).

## 4. Минимальность изменений
- Изменять только файлы, относящиеся к задаче.
- Никакого попутного рефакторинга («пока я здесь»).
- Не менять формат сохранений без миграции.
- Не трогать submodule `godot-cpp` и сгенерированные файлы.

## 5. Обязательная проверка (DoD)
- Проверки выбираются по затронутой области; полный порядок — в [GEMINI.md](../../GEMINI.md). Код считается готовым только после:
  1. `git diff` без лишних изменений.
  2. Успешного headless импорта Godot, если затронуты скрипты, сцены, ресурсы или настройки игры.
  3. Успешного прогона подходящих тестов; для комплексных изменений игры — `python tools/verify.py`.
  4. Сборки C++ (если затронут нативный код).
  5. Проверки реального запуска и отсутствия runtime ошибок, если изменено поведение игры.
  6. Проверки всех критериев приёмки (Acceptance Criteria).
- Для изменений только документации достаточно проверки ссылок, команд, согласованности правил и diff; сборка/запуск игры не требуются.
